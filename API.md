# UBB FMI Timetable Service API

Complete consumer-facing documentation for the static JSON API published by the UBB FMI Timetable Service.

## Base URL

```text
https://ronuhz.github.io/ubborarservice
```

The API is read-only and consists of static JSON files published through GitHub Pages. No API key, bearer token, OAuth flow, or other authentication is required.

## Quick Start

Start by fetching the catalog:

```http
GET /catalog.json
```

The catalog tells clients which academic years, programs, study years, and groups are available. Once a selection has been made, construct the timetable path as:

```http
GET /{academicYear}/{programId}/y{year}/g{group}.json
```

Example:

```text
https://ronuhz.github.io/ubborarservice/2025-2026/informatica-linia-de-studiu-maghiara/y2/g521.json
```

## Endpoints

| Endpoint | Description | Current contract |
| --- | --- | --- |
| `GET /catalog.json` | Available academic years, programs, study years, and groups | v1 |
| `GET /{academicYear}/{programId}/y{year}/g{group}.json` | Timetable for one group | v2 |
| `GET /rooms.json` | Room code to address mappings | rooms schema |
| `GET /announcements.json` | Operational and app announcements | v1 |
| `GET /discounts.json` | Discount cards and display metadata | v1 |

`.scrape-status.json` is also generated by the pipeline, but it is an operational artifact rather than part of the stable consumer API.

## Catalog

```http
GET /catalog.json
```

The catalog is the discovery endpoint. Clients should use it instead of hard-coding the available programs and groups.

### Response

```json
{
  "version": 1,
  "generatedAt": "2026-09-16T10:24:59Z",
  "academicYears": ["2025-2026"],
  "programs": [
    {
      "id": "informatica-linia-de-studiu-maghiara",
      "title": "Informatica - linia de studiu maghiara",
      "years": [
        {
          "year": 2,
          "groups": [521, 522, 523]
        }
      ]
    }
  ]
}
```

### Top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `version` | integer | Catalog contract version. Minimum value is `1`. |
| `generatedAt` | ISO 8601 datetime | Time at which the catalog artifact was generated. |
| `academicYears` | array of strings | Unique academic years in `YYYY-YYYY` format. |
| `programs` | array of `Program` | Programs currently available through the service. |

### Program

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Stable program identifier used in timetable paths. |
| `title` | string | Human-readable program name. |
| `years` | array of `StudyYear` | Available study years for the program. |

### StudyYear

| Field | Type | Description |
| --- | --- | --- |
| `year` | integer | University study year, starting at `1`. |
| `groups` | array of integers | Unique group numbers available for that study year. |

### Recommended discovery flow

1. Fetch `/catalog.json`.
2. Select an `academicYear`.
3. Select a program and retain its `id` as `programId`.
4. Select one of the program's study years.
5. Select a group advertised by that study year.
6. Construct the timetable URL using those values.

## Group Timetable

```http
GET /{academicYear}/{programId}/y{year}/g{group}.json
```

Returns the normalized timetable for one group.

### Path parameters

| Parameter | Type | Example | Description |
| --- | --- | --- | --- |
| `academicYear` | string | `2025-2026` | Academic year from the catalog. |
| `programId` | string | `informatica-linia-de-studiu-maghiara` | Program ID from the catalog. |
| `year` | integer | `2` | Study year. |
| `group` | integer | `521` | Group number. |

Example request:

```http
GET /2025-2026/informatica-linia-de-studiu-maghiara/y2/g521.json
```

### Response

Timetable payloads currently use contract version 2.

```json
{
  "version": 2,
  "generatedAt": "2026-09-16T10:24:51Z",
  "academicYear": "2025-2026",
  "programId": "informatica-linia-de-studiu-maghiara",
  "year": 2,
  "group": 521,
  "lastUpdatedAtSource": "2026-05-21",
  "days": [
    {
      "day": "monday",
      "entries": []
    }
  ]
}
```

### Top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `version` | integer | Timetable contract version. Version 2 is currently required. |
| `generatedAt` | ISO 8601 datetime | When this JSON artifact was generated by the service. |
| `academicYear` | string | Academic year in `YYYY-YYYY` format. |
| `programId` | string | Program identifier. |
| `year` | integer | Study year. |
| `group` | integer | Group number. |
| `lastUpdatedAtSource` | `YYYY-MM-DD` string or `null` | Last update date reported by the upstream timetable source. |
| `days` | array of `TimetableDay` | Timetable entries grouped by weekday. |

`generatedAt` and `lastUpdatedAtSource` have different meanings. `generatedAt` is generated by this service. `lastUpdatedAtSource` describes the upstream timetable and may be `null`.

### TimetableDay

```json
{
  "day": "monday",
  "entries": []
}
```

`day` is one of:

- `monday`
- `tuesday`
- `wednesday`
- `thursday`
- `friday`

### TimetableEntry

Every v2 entry contains the following required fields:

```json
{
  "time": "12–14",
  "frequency": "week1",
  "course": "Retele de calculatoare",
  "type": "lab",
  "room": "lambda",
  "roomAddress": "Cladirea Mathematica (str. Ploiesti, nr. 23-25)",
  "instructor": "Asist. SANDOR Csanad",
  "audience": {
    "formation": "521/1",
    "scope": "subgroup",
    "expectedScope": "subgroup",
    "isStandard": true
  }
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `time` | string | yes | Human-readable time interval from the timetable source. |
| `frequency` | enum | yes | `weekly`, `week1`, or `week2`. |
| `course` | string | yes | Course name. |
| `type` | enum | yes | `lecture`, `seminar`, or `lab`. |
| `room` | string | yes | Room identifier. May be empty if no room is supplied. |
| `roomAddress` | string | no | Resolved room/building address when available. |
| `instructor` | string | yes | Instructor text from the source. May be empty if unavailable. |
| `audience` | `Audience` | yes | Formation and audience-scope metadata. |

`time` is intentionally a string. Consumers should not assume an ISO time representation or parse it as a timestamp without their own normalization logic.

### Frequency

`frequency` has exactly three values:

| Value | Meaning |
| --- | --- |
| `weekly` | Activity occurs every teaching week. |
| `week1` | Activity belongs to the first alternating-week schedule. |
| `week2` | Activity belongs to the second alternating-week schedule. |

The API exposes the source frequency classification. Mapping `week1` and `week2` to a particular calendar date is a client concern and should follow the relevant academic calendar.

### Activity Type

`type` has exactly three values:

| Value | Normal expected audience scope |
| --- | --- |
| `lecture` | `cohort` |
| `seminar` | `group` |
| `lab` | `subgroup` |

The expected scope is also exposed explicitly through `audience.expectedScope`.

## Audience Metadata

Audience metadata was introduced as a required part of timetable contract v2.

```json
{
  "formation": "521/1",
  "scope": "subgroup",
  "expectedScope": "subgroup",
  "isStandard": true
}
```

### `formation`

Type: `string | null`

Preserves the formation identifier from the source when it can be identified. It is `null` when the formation is absent or ambiguous.

Possible source identifiers include values such as:

```text
IM2
521
521/1
521/2
```

Consumers should not derive audience scope only from the visual shape of this string. The backend performs the classification using source configuration and detected/configured groups.

### `scope`

The actual classified audience scope.

Allowed values:

| Value | Meaning |
| --- | --- |
| `cohort` | Applies to a larger program/year cohort. |
| `group` | Applies to a group. |
| `subgroup` | Applies to a subgroup. |
| `unknown` | Formation could not be classified confidently. |

Cohort identifiers are explicitly configured per academic year, program, and study year. The parser does not infer cohort membership merely from a URL or token shape.

### `expectedScope`

The structurally expected scope based on the activity type.

Allowed values are `cohort`, `group`, and `subgroup`.

The mapping is:

```text
lecture  -> cohort
seminar  -> group
lab      -> subgroup
```

### `isStandard`

Boolean indicating whether a known classified scope matches the normal scope expected for the activity type.

Standard example:

```json
{
  "formation": "521",
  "scope": "group",
  "expectedScope": "group",
  "isStandard": true
}
```

Non-standard example:

```json
{
  "formation": "IM2",
  "scope": "cohort",
  "expectedScope": "group",
  "isStandard": false
}
```

`isStandard: false` does not mean that the timetable entry is invalid. It only indicates that the known audience scope differs from the normal scope for that activity type.

Unknown formations deliberately use `isStandard: true`, so clients do not accidentally hide an entry just because the service could not classify its audience.

### Recommended client behavior

Do not discard an entry solely because `isStandard` is `false`.

The API exposes structural metadata. How that information is presented, filtered, or worded in the UI remains a client decision.

Cached or retained timetable v1 payloads do not have guaranteed audience metadata. Clients migrating from v1 should default those entries to visible until they successfully refresh to v2.

## Rooms

```http
GET /rooms.json
```

Returns mappings between room codes and addresses.

### Response

```json
{
  "rooms": [
    {
      "code": "lambda",
      "address": "Cladirea Mathematica (str. Ploiesti, nr. 23-25)"
    }
  ]
}
```

### Fields

| Field | Type | Description |
| --- | --- | --- |
| `rooms` | array of `Room` | Room mappings. |
| `rooms[].code` | string | Non-empty room identifier. |
| `rooms[].address` | string | Human-readable address. |

Timetable entries may already contain `roomAddress`, so consumers do not necessarily need a separate room lookup for each entry.

Unlike the catalog, timetable, announcements, and discounts contracts, the current rooms schema does not define a top-level `version` or `generatedAt` field.

## Announcements

```http
GET /announcements.json
```

Returns manual and automatically generated operational announcements.

### Response

```json
{
  "version": 1,
  "generatedAt": "2026-09-16T10:24:59Z",
  "items": [
    {
      "id": "example",
      "title": "Example announcement",

      "severity": "info",

  ]

```

### Announcement fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | string | yes | Non-empty stable announcement identifier. |
| `title` | string | yes | Non-empty title. |
| `message` | string | yes | Non-empty message body. |
| `severity` | enum | yes | `info`, `warning`, or `critical`. |
| `symbolName` | string | no | Optional symbol name for client presentation. |
| `startsAt` | ISO 8601 datetime | no | Optional start of the announcement validity window. |
| `endsAt` | ISO 8601 datetime | no | Optional end of the announcement validity window. |

The build pipeline can automatically inject a warning announcement when timetable scraping reports failures.

{

  "green": 0.5,

    blue: color.blue
)

## HTTP and Error Behavior

The service is a static, read-only API. Consumers only need `GET` requests. There are no `POST`, `PUT`, `PATCH`, or `DELETE` API operations.

Because endpoint paths correspond to published files, a path that is not present should be treated as a missing resource rather than as a structured API error response. Do not expect a JSON error envelope for invalid combinations of academic year, program, year, or group.

Use `catalog.json` as the source of truth for discoverable timetable paths.

Clients should check the HTTP status before attempting to decode a response as one of the documented JSON contracts.

The service does not define an application-level rate-limit contract. Consumers should cache responses and avoid unnecessary polling.

---

## Failure and Stale-Data Behavior

The publishing pipeline is designed to degrade gracefully when an upstream timetable source fails.

- A source-level failure does not stop other sources from processing.
- Existing timetable files remain valid when their source fails.
- With `--soft-fail-empty`, missing new files can be created as empty timetable payloads.
- `.scrape-status.json` records operational failures and warnings.
- The announcement builder can publish a warning when failures occur.

An empty timetable should therefore not automatically be interpreted as proof that a student has no classes. Clients that need to communicate service health should also consider the announcement feed.

For client-side failures, keep a known-good cached timetable when a refresh fails rather than immediately deleting it.

## Versioning and Compatibility

Timetable responses currently use version 2. The v2 schema requires `version` to be exactly `2` and requires audience metadata on every timetable entry.

Catalog, announcements, and discounts currently use version 1. Their schemas permit integer versions starting at `1`.

The rooms schema currently has no version field.

### Timetable v1 compatibility

Older cached or retained timetable v1 data has no guaranteed `audience` object. A client that still has v1 data should keep entries visible by default until a successful v2 refresh is available.

Consumers should avoid assuming fields from a newer contract are present when decoding older cached data.

---

## Caching Recommendations

The service is intentionally designed around static, cacheable JSON artifacts.

A typical mobile-client flow is:

```text
App launch
   |
   v
Load known-good local cache
   |
   v
Render immediately
   |
   v
Fetch current API artifact
   |
   v
Check HTTP response and decode contract
   |
   v
Replace cache only after successful decoding
   |
   v
Refresh UI
```

Recommended behavior:

- Cache successful timetable responses locally.
- Do not destroy a valid cache because a network request failed.
- Use `generatedAt` to understand when an artifact was generated.
- Use `lastUpdatedAtSource` separately to represent upstream timetable freshness.
- Refresh the catalog when program/group availability may have changed.
- Do not aggressively poll static endpoints.

## Swift Integration

### Base URL

```swift
import Foundation

enum UBBAPI {
    static let baseURL = URL(
        string: "https://ronuhz.github.io/ubborarservice"
    )!
}
```

### Models

```swift
struct Timetable: Codable {
    let version: Int
    let generatedAt: Date
    let academicYear: String
    let programId: String
    let year: Int
    let group: Int
    let lastUpdatedAtSource: String?
    let days: [TimetableDay]
}

struct TimetableDay: Codable {
    let day: Weekday
    let entries: [TimetableEntry]
}

struct TimetableEntry: Codable {
    let time: String
    let frequency: Frequency
    let course: String
    let type: ActivityType
    let room: String
    let roomAddress: String?
    let instructor: String
    let audience: Audience
}

struct Audience: Codable {
    let formation: String?
    let scope: AudienceScope
    let expectedScope: ExpectedAudienceScope
    let isStandard: Bool
}

enum Weekday: String, Codable {
    case monday
    case tuesday
    case wednesday
    case thursday
    case friday
}

enum Frequency: String, Codable {
    case weekly
    case week1
    case week2
}

enum ActivityType: String, Codable {
    case lecture
    case seminar
    case lab
}

enum AudienceScope: String, Codable {
    case cohort
    case group
    case subgroup
    case unknown
}

enum ExpectedAudienceScope: String, Codable {
    case cohort
    case group
    case subgroup
}
```

`generatedAt` is a full ISO 8601 datetime. `lastUpdatedAtSource`, however, is a date-only value such as `2026-05-21`, so keeping it as `String?` is often simpler than applying the same date decoder to both fields.

### Build a timetable URL

```swift
func timetableURL(
    academicYear: String,
    programId: String,
    year: Int,
    group: Int
) -> URL {
    UBBAPI.baseURL
        .appending(path: academicYear)
        .appending(path: programId)
        .appending(path: "y\(year)")
        .appending(path: "g\(group).json")
}
```

### Fetch the catalog

```swift
func fetchCatalog() async throws -> Catalog {
    let url = UBBAPI.baseURL.appending(path: "catalog.json")
    let (data, response) = try await URLSession.shared.data(from: url)

    guard
        let response = response as? HTTPURLResponse,
        response.statusCode == 200
    else {
        throw URLError(.badServerResponse)
    }

    let decoder = JSONDecoder()
    decoder.dateDecodingStrategy = .iso8601
    return try decoder.decode(Catalog.self, from: data)
}
```

## JavaScript Example

```javascript
const BASE_URL = "https://ronuhz.github.io/ubborarservice";

async function getTimetable(academicYear, programId, year, group) {
  const url =
    `${BASE_URL}/${academicYear}/${programId}/y${year}/g${group}.json`;

  const response = await fetch(url);

  if (!response.ok) {
    throw new Error(`Timetable request failed: ${response.status}`);
  }

  return response.json();
}

const timetable = await getTimetable(
  "2025-2026",
  "informatica-linia-de-studiu-maghiara",
  2,
  521
);

console.log(timetable);
```

## Publication Pipeline

The API is generated rather than dynamically served.

```text
Public UBB FMI timetable pages
            |
            v
      scripts/scrape.py
            |
            +------> per-group timetable JSON
            |
            v
      scrape status
        /       \
       v         v
 catalog builder  announcement builder
       |                 |
       v                 v
 catalog.json      announcements.json

 rooms + discounts
        |
        v
       dist/
        |
        v
   GitHub Actions
        |
        v
     gh-pages
        |
        v
https://ronuhz.github.io/ubborarservice
```

The default workflow publishes `dist/` to the `gh-pages` branch. It runs daily at `06:00 UTC`; during July and August, only Monday runs are executed.

## Client Design Notes

Treat `catalog.json` as the discovery mechanism instead of maintaining a separate hard-coded program/group database.

Preserve the complete v2 `audience` object even if a client does not currently display all of its fields. In particular, do not duplicate the backend's formation-classification logic by guessing from strings such as `521/1` or `IM2`.

Treat `isStandard` as metadata, not validity. A non-standard entry may be legitimate and should not automatically be hidden.

Treat unknown formations conservatively. The service intentionally marks them in a way that allows clients to keep the associated timetable entries visible.

Cache known-good data and replace it only after a successful fetch and decode. This complements the backend's own failure strategy, which preserves existing published timetable artifacts when an upstream source fails.

## Source of Truth

The JSON schemas in [`schemas/`](./schemas/) are the machine-readable source of truth for payload structure. If this document and a schema ever disagree about a structural constraint, follow the schema and update this documentation accordingly.
